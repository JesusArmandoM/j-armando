# ADR 0002 — Drizzle ORM is the data-access layer

- Status: accepted
- Date: 2026-10-12
- Decided during: Session 004 (`bootstrap-database-schema`)
- Source spec: `docs/specs/bootstrap-database-schema.md`

## Context

The store needs a real PostgreSQL data layer (catalog, cart, order and account schema from `docs/domain-model.md`), a reviewable migration story, and a typed query surface that later features build on. `docs/technical-discovery.md` had explicitly left the ORM / data-access layer undecided ("Drizzle vs Prisma vs raw SQL"), and `docs/risks-and-open-questions.md` tracked it as an implementation-time question that `bootstrap-database-schema` must resolve. Constraints from the surrounding decisions:

- Deployment target is Vercel with managed PostgreSQL (Neon or Supabase undecided — everything must connect through `DATABASE_URL`).
- The automated gate (`./init.sh`) must stay self-contained on machines with no Docker and no system PostgreSQL.
- Schema work must produce SQL migrations that are generated once, committed and never hand-edited afterwards.

## Decision

Use **Drizzle ORM** (`drizzle-orm` + `drizzle-kit` over the `pg` node-postgres driver), with the schema in `db/schema/` and SQL migrations in `db/migrations/` generated by `drizzle-kit generate`.

Reasons:

- **TypeScript-first, no codegen step.** Tables are plain TS; query types are inferred and there is no generated client or query-engine binary. Prisma requires `prisma generate` and ships an engine — extra build surface and a heavier serverless footprint on Vercel for no benefit at this size.
- **SQL-shaped and transparent.** `drizzle-kit generate` emits reviewable SQL; applied migrations are tracked in `drizzle.__drizzle_migrations`, so `db:migrate` is naturally idempotent (acceptance scenarios 1–2 of the spec).
- **Expresses the PostgreSQL features this domain needs**: enums (product/lifecycle states), CHECK constraints (`stock_qty >= 0`, positive quantities, lowercase email) and unique constraints (`(product_id, size, color)` for variants).
- **Driver-portable.** The same schema runs unchanged over `pg` in dev/tests and a Neon serverless driver in deployment, which keeps the provider swappable behind `DATABASE_URL` and matches the port/adapter layering in `ARCHITECTURE.md`.

Rejected alternatives:

- **Raw SQL** — rejected: it hand-rolls migration tracking and type safety for every query.
- **Prisma** — rejected for toolchain weight (engine binary, `prisma generate` step) and codegen ceremony. Revisit only if the team later wants Prisma's admin tooling.

Companion choices made here (see `ARCHITECTURE.md` and `CONSTRAINTS.md`):

- Money is stored as **integer cents** (`bigint`), `currency char(3) default 'USD'`; catalog prices are tax-exclusive.
- Migrations are generated once and committed; **never edit an applied migration** — generate a new one.
- The automated test suite boots an **ephemeral embedded PostgreSQL 17** (`embedded-postgres` package) per run; it requires no Docker and no system PostgreSQL.
- `db/` TypeScript scripts run with **Node 24 native type stripping** (erasable syntax only, explicit `.ts` import extensions).

## Consequences

- Every later feature writes queries through Drizzle against the committed schema instead of re-deciding tables; schema changes happen as new migrations.
- `pnpm db:generate` / `pnpm db:migrate` are the schema workflow; `pnpm db:seed` / `pnpm db:verify` cover the demo catalog.
- A future switch to Prisma or raw SQL would mean replacing `db/` and regenerating migrations from scratch; the committed SQL migration history would not transfer automatically.
- The managed-database choice (Neon vs Supabase) stays open: the schema and tooling only assume `DATABASE_URL`.
