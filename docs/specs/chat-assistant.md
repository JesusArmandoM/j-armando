# Feature Implementation Spec: Shopper talks to the chat assistant on the storefront

## Source Feature

- `id`: `chat-assistant`
- `area`: `ai`
- `depends_on`: `["catalog-product-listing"]` (accepted 2026-10-13)
- `status`: `not_started` at planning time
- `source`: `feature_list.json`

## Goal

Add a quiet, storefront-wide chat panel that lets a guest (or customer) ask product, sizing, fabric and shipping questions and receive an answer generated by a real LLM. The answer is produced behind a repo-owned `ChatAssistant` port, so the concrete LLM provider is an adapter that can be replaced without touching the UI. The UI talks only to a server endpoint (`POST /api/chat`); it never knows which provider is configured.

### Resolved open questions

- **LLM provider selection** (research task in `docs/risks-and-open-questions.md`; the feature notes cited blocking #2/#5, which are in fact the virtual-try-on provider and shipping-cost rules — a mis-citation. The actual blocking item for this feature is the LLM provider). Decision: **OpenAI Chat Completions** as the first adapter, model configurable via `CHAT_ASSISTANT_MODEL` (default `gpt-4o-mini`), key via `OPENAI_API_KEY`. **To be recorded by the implementer** in `docs/risks-and-open-questions.md` → Resolved and `docs/technical-discovery.md` → Integrations (planner could not edit those files in this runtime; see Durable Documentation Impact).
- **Chat scope** (blocking #4, split with the sibling feature). This feature defines the *topics* the assistant is prompted to help with — products, sizing, fabric/care, shipping — and the panel. It does **not** implement policy grounding, "I do not know" refusal, or price verification; those are `chat-assistant-guardrails`.
- **Conversation persistence.** The domain model has `Conversation`/`Message`, but this feature's verification only requires asking a question and seeing an answer. Decision for this slice: conversations are **ephemeral** — the panel holds message history in React state and sends the full history with each request; the server is stateless and touches no database. Persistence/ownership ("guest conversations may be unowned") is a follow-up feature. This keeps the feature's test suite database-free and avoids a speculative migration.
- **Streaming.** Non-streaming for this slice: one request returns the complete answer. Streaming is a follow-up, not required by the acceptance scenarios.

## Non-Goals

- Guardrails: refusing out-of-scope asks, never inventing shipping costs/return policies/prices, verified-price answers (owned by `chat-assistant-guardrails`).
- Conversation/Message persistence, conversation ownership, or attaching a guest conversation to an account after sign-in.
- Token streaming, retries/backoff, rate limiting/cost caps, moderation, or analytics on chat latency.
- Product-aware retrieval/tool-calling against the catalog (a possible later grounding feature; `chat-assistant-guardrails` is where pricing correctness lands).
- Any change to catalog, cart, identity or checkout behavior.

## Job Story

When I am browsing the store and have a question about a garment, its sizing, its fabric, or shipping,
I want to open an assistant panel and ask in plain language,
so I can get a useful answer without leaving the page or contacting support.

## Users And Permissions

- **Guest**: may open the panel and chat; no credentials required (`docs/user-and-access-model.md`).
- **Customer / Admin**: same as guest for this feature; no role gating.
- The panel is read-only storefront surface; it never exposes other users' data and sends no personal data beyond what the shopper types.

## Acceptance Scenarios

### Scenario 1: Product, sizing, fabric and shipping questions each return an answer

Given a configured `ChatAssistant` (a fake adapter in automated tests)
When the shopper sends a question about a product, then a sizing question, then a fabric/care question, then a shipping question
Then the panel shows the user's message followed by the assistant's reply in every case
And each reply is non-empty and the shopper's exact question was forwarded to the assistant
And replies are rendered as assistant bubbles distinct from the shopper's bubbles.

### Scenario 2: Answers come from the real LLM provider behind the interface

Given `OPENAI_API_KEY` (and optionally `CHAT_ASSISTANT_MODEL`) are configured
When `POST /api/chat` receives `{ "messages": [...] }`
Then the OpenAI adapter issues an HTTPS request to the provider's chat-completions endpoint with the configured model, a bearer `Authorization` header, and the conversation as `messages`
And the route returns the provider's message content as `{ "reply": "<content>" }`
And the automated gate proves this wiring with an injected `fetch` (no live network call), while a manual run against the real provider is recorded as evidence.

### Scenario 3: Swapping the implementation needs no UI change

Given the UI calls only `POST /api/chat` and imports only the `ChatAssistant` port types
When the adapter behind the port is replaced with another `ChatAssistant` implementation (as the tests do by injecting a fake)
Then the panel renders the new implementation's reply unchanged, with no edits to panel component, styles, or fetch call.

### Scenario 4: Provider errors and missing configuration degrade gracefully

Given the LLM provider returns an error/timeout, or `OPENAI_API_KEY` is unset
When the shopper sends a message
Then the panel shows a clear English error line (not a crash) and stays usable for another attempt
And `POST /api/chat` responds with a non-2xx status rather than a fabricated answer.

### Scenario 5: The panel opens and closes accessibly

Given any storefront page with the panel mounted
When the shopper activates the launcher
Then the panel opens with a labelled text input and a send control
And the launcher has an accessible name and the closed/open states are distinguishable by more than color
And on close the launcher is restored and reachable by keyboard.

## Technical Approach

1. **Port** — `lib/chat/chat-assistant.ts`: define `ChatMessage` (`{ role: "user" | "assistant"; content: string }`), `ChatAnswer` (`{ content: string }`), the `ChatAssistant` interface (`answer(messages: ChatMessage[]): Promise<ChatAnswer>`), and the store system prompt (English; scoped to products, sizing, fabric/care and shipping; concise). No provider detail leaks here.
2. **Adapter** — `lib/chat/openai-chat-assistant.ts`: `createOpenAiChatAssistant({ apiKey, model, baseUrl?, fetch? })` returning a `ChatAssistant`. It POSTs to `${baseUrl}/chat/completions` with `Authorization: Bearer <key>`, `model`, `messages` (system prompt + history), a low `temperature`, and parses `choices[0].message.content`. `fetch`, `baseUrl` and `model` are injectable so the contract can be tested offline. Errors (non-2xx, malformed body, thrown fetch) surface as a typed `ChatAssistantError`.
3. **Factory** — `lib/chat/index.ts`: `getChatAssistant()` reads `OPENAI_API_KEY`, `CHAT_ASSISTANT_MODEL` (default `gpt-4o-mini`) and optional `OPENAI_BASE_URL` lazily, caches one instance, and throws a clear configuration error when the key is missing. No module-level throw (the build must succeed without a key).
4. **Route** — `app/api/chat/route.ts`: `export async function POST(request)` validates the body (`messages` is a non-empty array of `{ role, content }`), calls `getChatAssistant().answer(messages)`, and returns `Response.json({ reply })`. Missing key / provider error → `Response.json({ error })` with 503/502; malformed body → 400. Marked dynamic. This is the only server seam the UI knows.
5. **UI** — `app/chat/chat-panel.tsx` (`"use client"`): floating launcher (bottom-right, fixed) that toggles a panel. Holds `messages` in state, an input, a send button, loading state and an error line. On send it appends the user message, `fetch("/api/chat", { method: "POST", body: JSON.stringify({ messages }) })`, then appends the reply (or shows the error). English copy; label "J. Armando Assistant"; zero-radius, hairline borders, tertiary/slate AI tint, Hanken Grotesk; circular AI status pip is the only rounded element (`DESIGN.md`). Mount once in `app/layout.tsx` so it is available on every storefront page.
6. **Env** — extend `.env.example` with commented `OPENAI_API_KEY`, `CHAT_ASSISTANT_MODEL`, `OPENAI_BASE_URL`.
7. **Tests** — see Verification Plan. All automated chat tests use injected/`mocked` `fetch` or a fake adapter; none call the network or a database.
