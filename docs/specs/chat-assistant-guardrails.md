# Feature Implementation Spec: Chat assistant does not invent store policies

## Source Feature

- `id`: `chat-assistant-guardrails`
- `area`: `ai`
- `depends_on`: `["chat-assistant"]` (accepted 2026-10-14; live provider verified 2026-10-19)
- `status`: `not_started` at planning time
- `source`: `feature_list.json`
- Worktree/branch: `chat-assistant-guardrails` / `feature/chat-assistant-guardrails`

## Goal

Make the storefront assistant safe to ship: it must never state a shipping cost, return policy, price or other store fact that is not backed by a verified source. Policies come from a repo-owned, versioned knowledge module (`lib/chat/guardrails/store-knowledge.ts`); prices come from the catalog database, published products only, formatted from integer cents. Anything the store has not published is answered with an explicit "I don't know", and clearly out-of-scope requests are declined without generating content.

The guarantee is **deterministic, not prompt-only**: policy, price, explicit sizing/product-info and out-of-scope questions are routed by a guardrail decorator before the LLM is called. The LLM is only used for open-ended in-scope conversation, with verified facts injected into its context and a post-generation check that discards fabricated dollar amounts. (The 2026-10-19 follow-up note below extends deterministic routing to generic category, sizing and explicit product-info asks.)

### Resolved decision (owns blocking open question #4)

- **Verified knowledge source:** `lib/chat/guardrails/store-knowledge.ts` — a code-reviewed, in-repo list of `VerifiedFact` records. Each fact has a stable `id`, topic matchers, an exact shopper-facing English `answer`, a `status` (`verified` | `not_published`) and a `source` reference to the durable document that justifies it. It is the **only** source the assistant may use for shipping, returns, payment methods and promotions. It is not generated by the LLM and is not fetched from the web.
- **Shipping cost and return policy today:** both are `not_published` and their exact answer begins "I don't know…". Shipping rules are still blocking open question #5 (owned by `checkout-shipping-method`); returns/refunds are explicitly outside MVP scope (`docs/mvp-scope.md`). This feature therefore answers those questions with an explicit unknown instead of inventing free shipping or a return window. When the store publishes those rules, only the knowledge module changes.
- **Price grounding:** a published product is resolved from the catalog DB, then its `basePriceCents` (integer cents, USD, tax-exclusive) is formatted with `formatPriceUSD` from `lib/money.ts`. The LLM never supplies a price. If no published product matches, the assistant says it has no verified price.
- **Refusal:** a deterministic topic router (`lib/chat/guardrails/intents.ts`) intercepts policy, price and out-of-scope asks. In-scope LLM answers receive the verified facts as context and pass through `guardLlmAnswer`, which replaces an answer containing an unverified dollar amount with an explicit "I can't confirm that price" reply.
- The durable architecture is recorded in a new `docs/adr/0004-chat-assistant-guardrails.md`; the skeleton is at the end of this spec because the planning runtime could only write under `docs/specs/`. The implementer updates `docs/risks-and-open-questions.md`: move blocking #4 to **Resolved** (do not touch #5).

## Non-Goals

- No chat persistence, no `Conversation`/`Message` migration, no conversation ownership.
- No cart, checkout, identity, catalog or payment changes.
- No RAG, embeddings, vector store, web search or live-provider fact fetching; the knowledge module is small and hand-curated.
- No per-variant price selection (variant selection is a separate feature); price answers use the product base price.
- No rate limiting, moderation, token streaming, retries or analytics changes.
- No UI redesign. The panel already renders any reply string; this feature changes server-side answer production only.
- No shipping-cost or returns policy decisions. Those stay with open questions #5 and the excluded returns flow.

## Job Story

When I ask the store assistant about shipping, returns, a price or something unrelated to the store,
I want an answer that is either backed by a real store source or an honest "I don't know",
so I do not act on a policy or price the store never agreed to.

## Users And Permissions

- **Guest / Customer / Admin:** identical; the chat is public and read-only. No authentication or role gate.
- The assistant exposes only published catalog data. Draft and archived products must never be named or priced.
- No personal data beyond the shopper's typed message is processed; nothing is persisted by this feature.

## Acceptance Scenarios

### Scenario 1: Shipping cost is verified or explicitly unknown (verification bullet 1a)

Given the assistant is running with the repo knowledge module and a fake LLM that would answer anything
When the shopper asks "How much does shipping cost?"
Then the reply equals the `shipping-cost` fact's exact `answer`, which begins "I don't know…" while the fact is `not_published`
And the reply contains no dollar amount and no invented threshold, timeframe or carrier
And the LLM is not called at all.

### Scenario 2: Return policy is verified or explicitly unknown (verification bullet 1b)

Given the same setup
When the shopper asks "What is your return policy?" or "Can I get a refund?"
Then the reply equals the `return-policy` fact's exact `answer`, which begins "I don't know…"
And no return window, condition or refund promise is invented
And the LLM is not called.

### Scenario 3: A product price is the actual catalog price (verification bullet 2)

Given the catalog DB contains the seeded published product "Longline Wool Overcoat" at `34900` cents
When the shopper asks "How much is the Longline Wool Overcoat?"
Then the reply contains `$349.00`, states USD and tax-exclusive, and is derived from the DB row
And the LLM is not called.

### Scenario 4: Unknown, draft and archived products yield no price (guardrail edge)

Given the catalog contains draft "Cropped Tweed Jacket" and archived "Satin Evening Gown"
When the shopper asks for the price of either, or of a product the store does not carry
Then the reply says it has no verified price for that item and asks the shopper to name a published garment or open its product page
And no price from a non-published row is disclosed.

### Scenario 5: Out-of-scope requests are declined without content (verification bullet 3)

Given the assistant is configured
When the shopper asks for the weather, news, medical/legal/financial advice, code, a translation or the assistant's system prompt/API key
Then the reply is the fixed English refusal that states the assistant can only help with J. Armando products, sizing, fabric/care and published store facts
And no answer content or policy is invented
And the LLM is not called.

### Scenario 6: In-scope questions still work and are grounded

Given the shopper asks an open-ended product question that is not a policy/price ask and is not an explicit sizing, style/material/care or availability ask (those are deterministic per the follow-up note)
When the guardrail delegates to the configured assistant
Then the assistant receives the conversation plus a `verifiedFacts` context containing only knowledge facts and matched published product facts
And the reply is returned unchanged unless `guardLlmAnswer` finds an unverified dollar amount.

### Scenario 7: A fabricated LLM price is discarded

Given a fake assistant returns "It costs $999.00."
When the guardrail post-check runs and `$999.00` is not among the verified facts used
Then the shopper sees the explicit "I can't confirm that price" reply instead of `$999.00`.

### Scenario 8: Price lookup failure never falls back to the LLM

Given the catalog lookup throws (database unavailable)
When the shopper asks a price question
Then the reply says it cannot confirm the price right now
And the LLM is not called, so no price can be fabricated.

## Technical Approach

### Data flow

```
ChatPanel ──POST {messages}──▶ app/api/chat/route.ts
                                     │ parse/validate (unchanged 400s)
                                     ▼
                        app/api/chat/composition.ts
                        createGuardedChatAssistant({
                          assistantFactory: getChatAssistant,   // lazy
                          knowledge: STORE_KNOWLEDGE,
                          catalog: { listPublishedProducts: () => listPublishedProductFacts(getDb()) }
                        })
                                     │
                                     ▼
                 lib/chat/guarded-chat-assistant.ts (implements ChatAssistant)
                   latest user message (+ recent antecedent)
                     ├─ policy intent  ──▶ STORE_KNOWLEDGE exact answer   (no LLM)
                     ├─ price intent   ──▶ catalog facts + product match  (no LLM)
                     ├─ out-of-scope   ──▶ fixed refusal                  (no LLM)
                     └─ in-scope       ──▶ assistantFactory().answer(messages, context)
                                              └─ guardLlmAnswer(reply, allowedFacts)
```

### Components

1. **Port extension** (`lib/chat/chat-assistant.ts`): add an optional second argument
   `answer(messages: ChatMessage[], context?: ChatAnswerContext): Promise<ChatAnswer>` with
   `ChatAnswerContext { verifiedFacts?: readonly string[]; instructions?: string }`. Existing callers/tests remain valid. Export `GUARDRAIL_INSTRUCTIONS` (grounding/refusal rules) from the guardrails module, not from the provider adapter.
2. **Adapter** (`lib/chat/openai-chat-assistant.ts`): build the system message as
   `CHAT_SYSTEM_PROMPT` + `context.instructions` + a bulleted "Verified store facts (the only authoritative source)" list + an explicit "never invent prices/policies; say you do not know" rule. User content is never concatenated into the system message.
3. **Knowledge module** (`lib/chat/guardrails/store-knowledge.ts`): export `VerifiedFact`
   (`id`, `topics`, `status`, `answer`, `source`), `STORE_KNOWLEDGE`, and `findFactsFor(message)`.
   Required initial facts:
   - `shipping-cost` (`not_published`) — answer: "I don't know the shipping cost. Shipping rates aren't published yet, so I can't confirm a price. Please contact the store for current shipping options." Source: `docs/risks-and-open-questions.md` #5.
   - `return-policy` (`not_published`) — answer: "I don't know the return policy. Return and refund terms aren't published yet, so I can't confirm them. Please contact the store before ordering." Source: `docs/mvp-scope.md` → Excluded (returns/refunds).
   - `tax-display` (`verified`) — "Catalog prices are shown in USD and exclude sales tax. Sales tax is calculated at checkout from your shipping address." Source: `CONTEXT.md`, `CONSTRAINTS.md` #1.
   - `market` (`verified`) — "J. Armando sells in the United States and prices everything in US dollars." Source: `CONTEXT.md`.
   - `payment-methods` (`not_published`) — answer: "I don't know which payment methods the store accepts. Payment options aren't published yet, so I can't confirm them. Please contact the store."
   - `promotions` (`not_published`) — answer: "I don't know about current promotions. Discounts and promo codes aren't published to me, so I can't confirm any offer. Please check the storefront or contact the store."
   Facts are answered verbatim; tests assert exact equality, no `$`, and that they begin "I don't know" for unknown facts.
4. **Intents** (`lib/chat/guardrails/intents.ts`): pure matchers.
   - `matchPolicyTopics(message)` → facts by keyword sets (shipping/delivery; return/refund/exchange; payment methods; discount/promo/coupon).
   - `hasPriceIntent(message)` → `price|pricing|cost|how much|expensive|cheap|$|USD|dollars`.
   - `isOutOfScope(message)` → clearly unrelated topics (weather, news/politics, sport, recipes, coding, homework/math, translation, medical/legal/financial advice, other retailers) and prompt-injection/system-prompt/key requests. Check only after no policy/price intent matched.
   - `OUT_OF_SCOPE_REPLY` — fixed English refusal naming the supported topics.
5. **Product matching** (`lib/chat/guardrails/product-match.ts`): pure `matchProducts(message, facts)`. Normalise case/punctuation, match full name, slug tokens, or distinctive name tokens; rank by matched token count and return all ties. Never fuzzy-match across a non-published set because the lookup only returns published rows. Used for price asks and to enrich in-scope product questions.
6. **Answer composition** (`lib/chat/guardrails/answer.ts` or inside the decorator):
   - Combine matched policy facts and a matched product price when both apply ("How much is the overcoat with shipping?").
   - Price reply uses `formatPriceUSD(basePriceCents)` and the currency, labelled tax-exclusive, e.g. "The Longline Wool Overcoat is $349.00 (USD, tax-exclusive)."
   - No product match → "I don't have a verified price for that. I can only quote prices for published catalog items — please name the garment or open its product page."
   - Multiple matches → list each matched published product's price and ask which one; never guess.
   - Catalog failure → "I can't confirm that price right now. Please try again in a moment."
7. **Post-generation guard** (`lib/chat/guardrails/answer-guard.ts`): `guardLlmAnswer(content, allowedFacts)` extracts `$` amounts from the reply and from the allowed formatted facts, then compares exact canonical amount strings (not substrings), so truncations like `$3`, `$34`, `$349` or `$349.0` do not inherit a verified `$349.00`. If any reply amount is not exactly one of the allowed amounts, return a fixed "I can't confirm that price…" reply. No other rewriting.
8. **Decorator** (`lib/chat/guarded-chat-assistant.ts`): `createGuardedChatAssistant({ assistantFactory, knowledge, catalog })` implements `ChatAssistant`. It resolves the last user message, falls back to the previous two user messages for a follow-up like "and how much is it?", and calls `assistantFactory()` only on delegation. Deterministic paths work with no provider key configured. For in-scope questions, a catalog failure only removes product facts from the context; it does not block the answer.
9. **Composition** (`app/api/chat/composition.ts`): `answerChat(messages)` builds the decorator with a lazy catalog adapter (`listPublishedProducts: () => listPublishedProductFacts(getDb())`) and `assistantFactory: getChatAssistant`. Both stay lazy so importing the module at build time opens no database pool and needs no key. This keeps `lib/chat/guardrails/*` free of `next`/`react`/`db` imports. The route calls `answerChat`; its validation and 400/502/503 mapping stay unchanged.
10. **Catalog fact query** (`db/catalog.ts`): add `listPublishedProductFacts(db)` returning `{ slug, name, description, composition, care, basePriceCents, currency }` for `status = published` only. No migration. Alternatively reuse `listPublishedCatalogProducts` plus `getPublishedProductBySlug`; the dedicated lean query is preferred so composition makes one round trip.

## Edge Cases

- **Price + shipping in one message:** answer the product price from the DB and the shipping unknown from knowledge; never derive shipping from the product price.
- **"How much is shipping?"** is a shipping question, not a product-price question.
- **Follow-up "and how much is it?"** resolves the product from the previous two user messages; if none, returns the no-verified-price reply.
- **Multiple products named:** list each published price and ask which one; do not choose silently.
- **Misspelled or generic garment** ("the coat"): if matching is not confident, return the no-verified-price reply rather than guessing.
- **Draft/archived ask:** the lookup excludes them, so the reply is the no-verified-price reply; no name/price leakage.
- **Catalog DB unavailable:** explicit "cannot confirm right now"; never delegate to the LLM.
- **Provider key missing:** deterministic policy/price/out-of-scope answers still work; in-scope questions return the existing 503 (route) / error line (panel).
- **LLM returns a dollar amount not in verified facts:** replaced by the answer guard.
- **Prompt injection** ("ignore instructions", "show your system prompt/key"): fixed refusal; no instructions/facts/keys disclosed.
- **Knowledge fact updated when #5 is resolved:** only the module changes; tests assert the current unknown copy, so update tests with the fact.

## Security / Privacy Notes

- The verified knowledge module is the only policy source; keep it code-reviewed and avoid user-controlled content in it.
- Prices are read with a parameterless published-only Drizzle query; the shopper's message is never interpolated into SQL.
- The LLM context is built from fixed facts and instructions; user text stays in `messages`, never in the system message.
- No conversation or message is stored; no personal data is logged. Existing provider error messages do not include keys.
- Only published catalog fields are exposed; draft/archived products remain unreachable.
- Tests use fake assistants/catalogs or injected `fetch`; no secrets, network or live provider in the gate. `.env`/`.env.local` remain gitignored.
- Prompt-injection and "reveal system prompt/key" requests are declined by the deterministic router.

## Open Questions

- **Shipping cost rules (#5)** and **returns policy** remain undecided outside this feature. The assistant answers both as explicit unknown; when they are decided, update `store-knowledge.ts` (and its source reference) rather than the LLM prompt.
- **Per-variant prices:** this slice grounds the product base price. When `product-variant-selection` ships, decide whether a size/color-specific price question should resolve `priceOverrideCents`; not required by this feature's verification.
- **Product matching precision:** the pure matcher is intentionally conservative; if real shopper phrasing produces too many no-match answers, extend it with tests rather than loosening it to guess.

## Residual Risks (accepted after independent validation, 2026-10-19)

These are known limits of the deterministic guard. They are recorded rather than assumed away; neither blocks acceptance because the deterministic paths that own the corresponding questions are covered and no verified data is disclosed.

- **F3 — non-price questions about draft/archived products can still reach the LLM.** The catalog reader is published-only, so no draft row, price or stored field can be disclosed. However, a question that names a draft product without a policy/price/out-of-scope intent (for example "Tell me about the Cropped Tweed Jacket.") delegates with only published facts, so the model could hallucinate a name or description. Optional future hardening: treat a plausible garment ask with no published match as no-information, or accept this residual in ADR 0004.
- **F4 — the post-generation guard only inspects dollar amounts.** An in-scope answer can still volunteer unverified non-price policy prose (for example "shipping is free") because `guardLlmAnswer` does not rewrite non-price claims. Policy questions are intercepted before the LLM, and the provider is instructed not to volunteer policies, but that part is mitigation rather than a deterministic guarantee. The guard discards unverified dollar amounts; it does not validate prose.
- **Guard behaviour is discard-only.** Any reply containing an unverified amount is replaced wholesale by `UNVERIFIED_PRICE_REPLY`; the guard never rewrites a price. Amounts are matched as exact normalized strings (`$` spacing and thousands separators normalized), so `$349.00` is accepted only when that exact amount appears in a verified fact, and `$3`, `$34`, `$349` or `$349.0` are rejected even when `$349.00` is allowed.
- **Live-provider prose quality is sampled, not guaranteed.** The optional live transcript covers four deterministic questions plus one in-scope question; ongoing provider wording is outside the automated gate.

## Follow-up implementation note (2026-10-19): catalog-grounded generic product questions

Live use after acceptance exposed three gaps: generic "coat" questions did not match the
published overcoat (the matcher was name/slug-only), the chat facts omitted category and variants
so sizing could not be answered, and the generic verb "offer" made "Do you offer free shipping?"
append the promotions unknown. The feature remains accepted; this follow-up keeps the same
verified-source principle and adds deterministic catalog grounding.

- `ProductFact` now carries `categorySlug`, `categoryName` and non-discontinued `variants`
  (`size`, `color`, `stockQty`). `listPublishedProductFacts` joins category and variants, remains
  published-only and needs no migration.
- `matchProducts` uses curated category synonyms (`coat/coats`, `overcoat`, `outerwear`,
  `blazer/sport coat`, `dress`, `sweater/knitwear`, `shirt`, `trousers/pants`). Multi-word
  synonyms outrank broad ones; a specific product mention still outranks its category.
  Ambiguous `jacket`/`gown` synonyms are excluded because they collide with the draft
  `Cropped Tweed Jacket` and archived `Satin Evening Gown`. Material-only asks still do not match.
- `hasSizingIntent` routes to `composeProductSizingAnswer`, built from published variants: sizes,
  colors and in-stock/out-of-stock pairs, followed by `NO_SIZE_CHART_REPLY` because the catalog has
  no body measurements or size chart. No measurement is invented.
- `hasProductInfoIntent` routes explicit style/material/care/details/availability asks to
  `composeProductInfoAnswer`, built from the published description, composition, care, sizes,
  colors and base price. Open-ended in-scope asks still delegate to the LLM with expanded
  `verifiedFacts`.
- `formatProductGroundingFact` now includes category, available sizes/colors and in-stock pairs.
- Shipping/promotions precedence: when shipping-cost matches, promotions are suppressed if the
  only trigger is the generic verb "offer"; explicit promo/discount/coupon/sale words keep them.
- Tests: focused chat suites 7 files / 71 tests; `./init.sh` 35 files / 261 tests. New coverage
  includes category matching, specific-over-category ranking, material-only no-match, variant
  grounding, deterministic sizing/product-info, the generic no-size-chart fallback, discontinued
  variants excluded from chat facts, and shipping/promotions routing.
- Residual: no body measurements/size chart are published, so fit guidance is limited to available
  sizes/stock plus a referral to the store; adding measurements is a content decision. Category
  synonyms are curated and must be reviewed when categories/products (especially unpublished
  names) change. F3/F4 above remain unchanged.

## Appendix: ADR 0004 skeleton (create as `docs/adr/0004-chat-assistant-guardrails.md`)

```md
# ADR 0004 — Chat guardrails use repo-owned verified facts plus catalog price grounding

- Status: accepted
- Date: 2026-10-19
- Decided during: `chat-assistant-guardrails`
- Source spec: `docs/specs/chat-assistant-guardrails.md`

## Context

The assistant previously relied on a prompt asking the LLM not to invent prices or policies.
A prompt is not a guarantee. Shipping cost rules are undecided (#5) and returns are outside MVP
scope, so no verified shipping/return policy exists yet. Catalog prices exist in PostgreSQL as
integer cents, USD, tax-exclusive. The gate must stay offline/key-free and AI capabilities stay
behind repo-owned ports.

## Decision

1. Verified policies live in `lib/chat/guardrails/store-knowledge.ts` as reviewed facts with an
   exact answer, a `verified` | `not_published` status and a source reference. Unpublished facts
   answer with an explicit "I don't know".
2. Prices come from the published-only catalog query in `db/catalog.ts`, formatted with
   `formatPriceUSD`; the LLM never supplies a price.
3. A `ChatAssistant` decorator (`lib/chat/guarded-chat-assistant.ts`) deterministically answers
   policy, price and out-of-scope asks without calling the LLM. In-scope answers get verified facts
   as context; `guardLlmAnswer` discards replies containing unverified dollar amounts.
4. `app/api/chat/composition.ts` wires knowledge, the DB-backed catalog reader and the lazily
   resolved provider behind the existing port.

## Reasons

- Guarantee, not prompt hope: deterministic paths are testable and provably never call the LLM.
- Honest unknowns until #5/returns are decided; closing the gap means editing one module.
- One reviewable policy source; the DB is already authoritative for integer-cent prices.
- Minimal architecture: no RAG, vector store, schema change or new provider.

## Rejected alternatives

- Prompt-only guardrails (not a guarantee; untestable without a live LLM).
- Copying shipping/return claims from the design assets (direction, not specification).
- Tool-calling/retrieval now (heavier than needed for six published products).
- Persisting conversations or guardrail decisions (out of scope; no migration).

## Consequences

- Risks #4 moves to Resolved; #5 stays blocking for `checkout-shipping-method`.
- When shipping/returns are decided, update `store-knowledge.ts` and its tests only.
- `ChatAssistant.answer` gains an optional grounding context; deterministic answers need no key.
- The gate remains offline/key-free; a live transcript is optional evidence.
```
